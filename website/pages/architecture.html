Architecture

Laptop, Mantle, Substrate, worker.

Mantle decides what development session you want and where it runs. Substrate decides nothing about products: it runs processes in confined workspaces on one host and reports what it observed. Mantle depends on Substrate through its SDK; Substrate has no Mantle code in it.

Workspaces live on an XFS data volume with project quotas at /var/lib/substrate.

Mantle never reports an isolation guarantee Substrate did not report. When the worker lacks a fact the session needs, the start is refused by name; Mantle does not fall back to an unconfined shell. Requested and applied resources are printed separately, and an execution whose outcome Substrate does not know is shown as unknown.

Where the boundaries are.

03 / Who owns what

Policy in Mantle, mechanism in Substrate.

From the design, §4, §7 and §8, reduced to what 0.2.0 implements.

Mantle owns

  • Session intent: the manifest, the agent, the runtime profile, the repositories, requested resources.
  • Placement and provisioning: one worker per configuration, on AWS or KubeVirt; bootstrap and helper installation.
  • Environment: the rust-dev toolchain under /opt/mantle, the agent adapters for Claude Code and Codex, the compiler and proxy environment.
  • Sources: HTTPS repositories at a branch, tag or commit; the checked-out commit is recorded.
  • Lifecycle: start, attach, detach, stop, restart, destroy, and the local record of each.
  • The egress allowlist, enforced by its gateway outside the sandbox.

Substrate owns

  • Creating the confined workspace and guarded file operations in it.
  • Running processes and PTYs, with output observation, cancellation, timeouts, leases and whole-tree cleanup.
  • Durable operation identity: an interrupted request can be observed again instead of repeated.
  • cgroup, quota and egress facts, and the facts each run actually applied.
  • The secret-slot mechanism and the authenticated host API on a Unix socket.

A session is the unit of placement: Mantle never places single cargo commands remotely. The terminal is not the session: closing an attachment leaves the agent running until its execution ends. Once a session starts, the remote workspace is the source of truth for it; edits do not mirror back to the laptop.

04 / Paths across boundaries

Control, credentials, network.

A. Control and terminal
The CLI opens SSH to the worker through a provider ProxyCommand: aws ssm start-session with AWS-StartSSHSession on EC2, virtctl port-forward --stdio on KubeVirt. The worker has no inbound port either way; the AWS security group has no ingress rule. SSH forwards the daemon’s Unix socket to a private local socket, and the CLI speaks the Substrate SDK over it. mantle attach opens a PTY session running mantle-launch attach, which relays to the agent through FIFOs in /workspace/.mantle/agent; the sandbox refuses Unix sockets, so tmux and screen do not run inside it.
B. Credentials
Claude: worker up writes the token from your laptop to /var/lib/mantle/secrets/claude on the worker; Substrate hands it to the agent execution through the claude secret slot on descriptor 3; the launcher moves it into the agent’s environment. Codex: device login in the agent terminal; the auth file lives in /workspace/.mantle/home/.codex. Details and limits: security model.
C. Network
The sandbox has no network of its own. Substrate declares one aperture, egress, to the host gateway at 127.0.0.1:3128. The gateway admits ten exact host:443 pairs: the list.

05 / Designed, not built

What the design describes and 0.2.0 does not do.

The design document is a proposal; its correction block lists where the first slice differs. These parts are not implemented:

  • A coordinator service, worker fleets, scheduling, Spot capacity and scale-out. Mantle 0.2.0 manages one worker named default; placement in a manifest is accepted and ignored.
  • Remote TLS with an identity provider. The CLI reaches Substrate over SSH, not HTTPS.
  • A Git credential broker, publishing back from Mantle, and starting from a dirty local checkout.
  • Session-to-session communication, shared build caches, workspace snapshots and recovery of a lost worker or volume.
  • Per-session network policy. The allowlist is fixed per worker.
